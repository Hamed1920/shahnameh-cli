# Sync Protocol (v1.0)

How prompts authored in **Claude Chat** or **Claude Cowork** get executed by **Claude Code CLI**
without anything drifting, colliding or getting lost.

---

## 1. The problem this solves

Prompts are written on a surface that cannot see this disk. The CLI can see the disk but did not
write the prompt. Left informal, three things break within a week:

1. **Naming drift.** Chat writes "the walking stick"; the CLI has three of them.
2. **ID collisions.** Chat invents `PRP-003`; the CLI has already assigned `PRP-003` to something
   else. Two objects, one number, silently.
3. **Lost provenance.** A file appears with no record of which prompt made it or why.

The fix is a closed loop with exactly one authority for each thing:

| Thing | Authority |
|---|---|
| What exists, and what it is called | **CLI** — `ENTITIES.csv` |
| Number assignment | **CLI**, always, no exceptions |
| Creative intent, prompt wording | **Chat / Cowork** |
| Execution and file layout | **CLI** |

Chat proposes. The CLI disposes. Chat is structurally incapable of causing a collision because
it never writes a number.

## 2. The loop

```
   [1] /sync-out                 [2] author                [3] /sync-in
CLI  ------------->  CONTEXT_PACK  ------------->  JOB  ------------->  CLI
                        |                                                |
                        |                                                v
                        |                                        assign IDs, execute,
                        |                                        file, log
                        |                                                |
                        +<------------- RECEIPT <------------------------+
                                            [4] paste back
```

1. **`/sync-out`** builds `00_PROJECT/sync/CONTEXT_PACK.md` — the complete, current, paste-ready
   state of the project. You paste or attach it into Chat / Cowork.
2. You work there. It emits one or more **JOB blocks**.
3. **`/sync-in`** ingests them: validates, reserves IDs, executes, files, logs.
4. The CLI prints a **RECEIPT block**. You paste that back into the same conversation so it
   learns the real IDs. Only needed if you're continuing in that conversation.

Steps 1 and 4 are the sync. Skip them and the loop degrades to guessing.

## 3. The CONTEXT PACK (CLI → Chat)

Generated by `00_PROJECT/tools/Build-ContextPack.ps1`, invoked by `/sync-out`.

It contains, and nothing else:

- The condensed naming rules and the JOB block schema
- Every entity: full ID, short ID, family, status, canonical variant, one-line description
- **Next free number per kind** — so Chat knows the shape of the space without allocating in it
- Open questions
- A generation timestamp and a state hash

**Use it like this:** in Claude Cowork, add it to the project's files so it persists. In Claude
Chat, paste it as the first message of a conversation, or attach it to a Project. Regenerate and
re-share whenever the CLI has added entities — the pack is cheap, staleness is not.

The pack ends with a `state_hash`. Chat echoes that hash in every JOB block it emits. If the hash
in an inbound job doesn't match the current registry, `/sync-in` warns you that the job was
written against a stale view of the project. It still runs — but you get told.

## 4. The JOB block (Chat → CLI)

Line-oriented headers plus one free-text body. Chosen over JSON deliberately: Higgsfield prompts
are long, multi-line, and full of commas, colons and quotes. Nothing here needs escaping.

```
=== SHM-JOB ===
job_id: J-20260903-001
author: claude-chat
state_hash: a1b2c3d4
type: generate.image
target: SHM-PRP-001-STAFF-COBRA-BRONZE
variant: V02
engine: higgsfield
refs: @CHR-001/V02; @PRP-001
params: ar=16:9; count=4
notes: needs to read at 1/3 frame height
--- prompt ---
Bronze hooded cobra staff, twisted dark wood shaft, museum turnaround
lighting, neutral grey seamless, full front and back plus head detail.
--- end prompt ---
=== END SHM-JOB ===
```

### Fields

| Field | Required | Notes |
|---|---|---|
| `job_id` | yes | `J-YYYYMMDD-NNN`. Unique. Re-pasting the same one is a safe no-op. |
| `author` | yes | `claude-chat`, `claude-cowork`, `human` |
| `state_hash` | no | From the context pack. Omitted means "unknown vintage". |
| `type` | yes | see below |
| `target` | yes | An existing full or short ID, **or** a `NEW/...` proposal |
| `variant` | no | `V02`. Omit and the CLI takes the next free variant. |
| `engine` | no | `higgsfield`, `midjourney`, `manual` |
| `refs` | no | `@` reference tokens, semicolon-separated |
| `params` | no | `key=value` pairs, semicolon-separated |
| `notes` | no | free text for the human |
| prompt body | for generate.* | between the `--- prompt ---` fences |

### Job types

| Type | Does |
|---|---|
| `generate.image` | Produce a still for an entity variant |
| `generate.video` | Produce a shot |
| `register.entity` | Create an entity with no asset yet |
| `update.entity` | Change status, canonical variant, description, flags |
| `retire.entity` | Retire an entity, burning its number |
| `define.shot` | Add or update a shotlist row |

### Proposing something new

Chat **never writes a number.** It writes a proposal:

```
target: NEW/PRP/STAFF-IRON-CAPPED
```

`KIND` plus the slug it wants. The CLI takes the next free number for that kind, creates the
entity at status `RESERVED`, and reports the real ID in the receipt. If the slug collides with an
existing one, the CLI rejects the job rather than creating a near-duplicate.

## 5. The RECEIPT block (CLI → Chat)

Short by design — it goes back into a conversation, so it must not eat the context window.

```
=== SHM-RECEIPT ===
state_hash: e5f6a7b8
J-20260903-001  OK        SHM-PRP-001-STAFF-COBRA-BRONZE V02  -> 04_PROPS/...V02_head-detail.png
J-20260903-002  ASSIGNED  NEW/PRP/STAFF-IRON-CAPPED -> SHM-PRP-011-STAFF-IRON-CAPPED (RESERVED)
J-20260903-003  REJECTED  unresolved ref @CHR-009
=== END SHM-RECEIPT ===
```

Paste it back into the conversation that produced the jobs. From that point Chat knows
`SHM-PRP-011` exists and will reference it correctly.

## 6. Getting jobs onto disk

Two paths, both supported:

- **File drop (preferred).** Save the job text to `00_PROJECT/sync/inbox/` as `.txt` or `.md`.
  Robust for long prompts and multi-job batches. Cowork can export a file directly.
- **Paste.** Paste the block straight into the CLI chat and say "ingest this". Fine for one or
  two short jobs.

After ingest, the source file moves to `00_PROJECT/sync/processed/` and the receipt is written to
`00_PROJECT/sync/receipts/`. The inbox is always either empty or a to-do list.

---

## 7. Guarantees

The system holds these, and the validator proves them:

1. **No collisions.** Only the CLI allocates numbers, and it allocates from the registry.
2. **No silent duplicates.** A `NEW/` proposal whose slug already exists is rejected, not merged.
3. **Idempotent ingest.** A job is keyed by `job_id` + a hash of its content. Re-pasting the same
   job is a no-op. Re-using a `job_id` with *different* content is a hard error.
4. **No dangling references.** Every `@token` must resolve to a file on disk before a job runs.
5. **No orphan files.** Every media file has a manifest row; every manifest row has a file.
   `/sync-check` fails otherwise.
6. **Full provenance.** Every generated asset traces back to the `job_id` and prompt that made it,
   via `sync/JOB_LEDGER.csv`.
7. **Reversible renames.** `original_filename` is preserved for every asset, forever.

---

## 8. Failure handling

| Failure | What happens |
|---|---|
| Malformed job block | Rejected, left in inbox, named in the receipt |
| Unknown `target` ID | Rejected. Never auto-created — that is how phantom entities appear. |
| Unresolvable `@ref` | Rejected before any generation spend |
| `NEW/` slug collides | Rejected with the colliding ID named |
| Stale `state_hash` | Warning, job still runs |
| Duplicate `job_id`, same content | Skipped, reported as `DUPLICATE` |
| Duplicate `job_id`, different content | Hard error, nothing ingested from that file |

Rejections never partially apply. A batch either ingests cleanly or the failing jobs are held
back with the rest still processed — and the receipt says exactly which was which.
